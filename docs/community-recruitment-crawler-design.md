# 东城区、朝阳区社区工作者招聘采集设计

设计日期：2026-10-13。第一阶段已实现：两个专用入口、分页与增量采集、东城官网搜索归档补漏、正文附件、SQLite历史、招聘阶段和报名窗口，以及内置任务注册。第二阶段岗位附件内容解析、第三阶段调度和结果页仍为后续设计。实际使用见`crawlers/README.md`。以下表格包含后续扩展目标，已实现输出以脚本和使用说明为准。

## 1. 现有覆盖与目标

| 地区 | 已有脚本 | 实际覆盖 | 社区招聘的缺口 |
| --- | --- | --- | --- |
| 东城区 | `crawlers/dongcheng_public_institutions.py` | 仅事业单位招录栏目首页，默认前10条；文章路径也限定在该栏目 | 社区招聘会发布于“通知公告”，不能只修改任务网址解决；也需要分页 |
| 朝阳区 | `crawlers/beijing_chaoyang_recruitment.py` | “其他招考”栏目，已有分页，默认收集最新10条；未专门区分社区招聘与招聘阶段 | 能抓社区信息，但原始招聘公告排到第11条以后就会遗漏；缺少报名状态和跨次运行跟踪 |

目标：新增两个社区工作者专用任务，全年使用固定栏目入口，自动发现任意年份、任意批次的新公告，保存正文及附件，并区分“新报名”和考试、成绩、拟录用等后续信息。

现有通用任务继续负责原来的采集范围。专用任务在控制台中分别命名为“东城区社区工作者招聘”“朝阳区社区工作者招聘”。

- [朝阳区2026年度公开招聘社区工作者公告](http://www.bjchy.gov.cn/affair/civilemployed/zhk/4028805a9e76c851019e85ee13d60ab9.html)位于“其他招考”。2026-10-13核查时，该原始公告已位于栏目第二页。

首期用官方栏目完成发现、正文和附件采集；保留报名网址。公招网和365社区系统的独立发现适配器，需检查真实页面结构后再接入，不把某一年的项目报名链接当作永久采集入口。

东城通知公告列表在2026-10-13试跑时只有40页，最早到2026-01-28，2025年招聘原文仍可访问但已经不在列表中。首期已接入官网搜索接口`https://www.bjdch.gov.cn/so/ss/query/s`，按日期范围和社区工作者标题关键词分页查询JSON，仅采集目标官方栏目的文章；逐页校验总数、重复结果和接口结构，保留原始搜索证据及独立增量水位。覆盖完整指可见栏目与搜索索引扫描完成，不保证未列出、未索引或站外的所有公告。

## 3. 文件及职责

| 文件 | 职责 |
| --- | --- |
| `crawlers/dongcheng_community_recruitment.py` | 东城入口；配置官方栏目、分页和正文适配器 |
| `crawlers/chaoyang_community_recruitment.py` | 朝阳入口；配置“其他招考”分页和正文适配器 |
| `crawlers/lib/community_recruitment.py` | 时间窗口、公告分类、报名时间提取、持久化、更新检测、统一输出；位于lib中，不注册为独立任务 |
| `crawlers/tests/test_community_recruitment.py` | 覆盖跨年、翻页、阶段识别、延期、恢复和去重的离线用例 |

沿用现有标准调用协议：`--url`、`--output-dir`、`--run-id`。两个入口脚本接受同一组附加参数。

复用北京市人社局脚本的请求、重试、日志和附件下载代码；两个地区各自配置栏目、分页和正文解析。官网搜索通过子类转换为表单POST，沿用相同请求间隔和重试机制。支持朝阳历史WPS附件，不直接调用“选满10条就停止”的选择逻辑。

首期核心采集和SQLite持久化使用Python标准库。Office/PDF岗位表内容解析属于第二期，需要单独声明和检查依赖；第一期已下载附件不代表已识别出岗位数量。

## 4. 长期发现策略

### 首次运行与日常增量

1. 首次没有历史状态时，默认回溯730天；支持指定起止日期进行历史补采。历史公告用于建立档案，不算作新一轮可报名机会。
2. 日常运行从“该来源上次完整扫描成功的日期减7天”开始，覆盖到北京时间今天。若停机一个月，就自动补扫一个月加重叠窗口，不能固定只查最近7天。
3. 按官方分页链接或已验证的分页模板继续读取，先遍历列表再筛选社区招聘，不能按“读到10条任意公告”停止。
4. 处理置顶、重复链接和日期缺失：不能遇到一条旧公告就停止。只有来源已验证按时间排序，连续两页非置顶有效条目均早于窗口且没有未知日期，才允许按日期停止；否则扫描到末页或显式上限。
5. 触及页数上限、循环分页、缺失列表容器或日期不能可靠解析时，写入“覆盖不完整”，不推进该来源的完整扫描水位。上限可调整，不能以0条结果伪装扫描成功。
6. 每次复查已登记的尚未开始、正在报名及状态待确认的公告；即使原公告已经滑出增量窗口，也能检测正文或附件中的更正。近期已截止公告保留30天复查期，发现延期通知时重新激活。
7. 每周建议做一次最近90天的补漏扫描；支持显式补采更早的范围。保留“本次覆盖起止日期”，不承诺覆盖网站未列出或历史归档中不可见的全部公告。

### 年份和批次

- 不在网址、文件名或筛选条件中写死2026、2027。
- 招聘年度从标题的明确年份提取；发布时间年份单独保存，无法确认招聘年度时为空。
- 2026年12月发布的2027年招聘正常入库；2026年12月开放、2027年1月截止的报名窗口跨年计算。
- 同一年可能有第二批、补招、追加或面向特定群体的计划，不能以“地区+年份”作为唯一键。

## 5. 公告筛选、招聘阶段和报名状态

先识别招聘对象，再识别阶段。主要对象关键词为“社区工作者”“专职社区工作者”“社区专职党务工作者”。“社工人才”“社会工作者培训”“社会工作者职业资格考试”等不直接当作社区招聘。

列表标题优先匹配对象关键词；对标题只有招聘、招考、招录、补招、补录、报名延期、更正或考试阶段等字样的候选公告，再读正文识别对象及关联批次。已知计划的关联通知也纳入。

| 公告阶段 | 如何处理 |
| --- | --- |
| 原始招聘、追加招聘 | 建立招聘计划，提取报名窗口 |
| 更正、延期、取消 | 保存变更事件，更新关联计划；无法确认关系时标记待核对 |
| 补招、补录 | 只有明确接受新的报名申请，才记作新的报名机会；按原成绩递补录用不算新报名 |
| 笔试、资格复审、面试、成绩 | 跟踪流程，不直接判定可以新报名 |
| 拟聘、拟录用、录用结果 | 跟踪结果，不直接判定可以新报名 |

报名状态单独保存为：`upcoming`（尚未开始）、`open`（正在报名）、`closed`（已截止）、`cancelled`（已取消）、`unknown`（待确认）。后续考试公告自身不产生报名窗口；当前按招聘原公告及明确关联的报名变更计算状态，其他阶段信息作为事件保留。

时间统一使用`Asia/Shanghai`。状态根据每个窗口的起止时间动态计算，支持多个不连续窗口和现场报名的每日时段。只给截止日期、不写时刻时，保留“日期精度”，当天标记需确认；不能自行推成23:59。确实缺少报名时间时输出待确认，并保留原文证据。

对“2027年1月5日至8日”等省略写法可明确补齐共享年份/月；对跨年或缺少年份有歧义的写法不猜测。延期须关联到同一批次，保存原截止时间、新截止时间和来源。来源冲突时显示待核对，不能只选择更晚的截止日期。

## 6. 持久化、去重与结果

跨次运行状态按地区分库存于`.crawler-console/community-recruitment/<district>.sqlite`。默认路径从脚本所在项目根目录推导，不能依赖进程工作目录；现有runner的工作目录是脚本目录。可用绝对路径`--state-dir`覆盖。

| 数据 | 关键字段 |
| --- | --- |
| 来源扫描状态 | 来源ID、完整扫描水位、上次尝试时间、覆盖范围、停止原因 |
| 公告 | 稳定公告ID、原始/规范网址、标题、发布日期、招聘年度、地区、正文与附件哈希、首次/最近发现时间 |
| 招聘计划 | 计划ID、单位、年度和批次、主公告、报名窗口、报名方式与网址、动态状态、原文依据 |
| 计划事件 | 关联公告、阶段、变更内容、关联依据；不确定的关联保持待核对 |
| 重试项目 | 页面/附件网址、错误、重试次数、下次重试时间 |

同网址再次抓取不重复新增公告；正文或附件哈希改变记为更新。保留原始链接，规范化只删除明确无关的追踪参数，不丢弃项目ID等有效查询参数。

跨来源转载只有能确认单位、年度、批次或明确原文链接相同，才合并为同一计划并保存全部来源；同标题不自动合并。同地区并发写入通过SQLite事务和运行锁协调。

列表扫描完成与详情/附件完成分别记录。扫描水位仅在本来源列表覆盖完整、候选发现已持久化后推进；详情或附件失败写入持久化重试队列。进程中断或事务失败不能丢弃待处理链接。存在失败项目时输出部分失败信息，即使进程正常退出也不能把岗位分析标成完整。

每次运行仍在runner提供的独立目录中输出：

```text
records.jsonl                 本次读取或更新的公告，沿用现有字段
catalog.json                  所有已登记计划的当前状态快照
summary.json                  新增/更新公告数、报名状态分布、覆盖情况
errors.jsonl                   页面及附件失败信息（无失败时为空）
search-pages/<page>.json       东城官网搜索请求参数及原始响应
articles/<article-id>.html     原始正文页面
attachments/<article-id>/     原始岗位表和报名材料
```

在原有记录上增加`recruitment`字段，包含`district`、`recruitment_year`、`campaign_id`、`announcement_type`、`application_windows`、`application_status`、`application_urls`及证据。保留现有记录的`status`表示解析质量，不能用它兼作报名状态。

原始资料每次运行独立保存，持久化索引维护去重历史，两者作用不同。现有runner统计的是`records.jsonl`行数，即“本次公告数”；社区专用结果另外显示“新增公告”“正在报名计划”，不能把这些数值冒充岗位数或招聘人数。

岗位数、招聘人数和资格筛选待附件解析可靠完成后才输出；缺失表格或解析失败用未知值，并显示统计是否完整，不能当成0。

## 7. 参数和控制台接入

| 参数 | 建议值/用途 |
| --- | --- |
| `--mode auto/incremental/backfill` | 默认auto：无状态首次补采，有状态日常增量 |
| `--lookback-days 730` | 首次补采范围；日常增量由扫描水位决定 |
| `--overlap-days 7` | 增量重叠范围 |
| `--from-date`、`--until-date` | 显式补采范围；与模式/回溯参数的冲突须校验 |
| `--max-pages 200` | 每来源扫描上限；触及上限须报告覆盖不完整 |
| `--state-dir` | 跨次运行索引的绝对目录 |
| `--request-delay 0.5` | 请求间隔，复用重试与超时机制 |
| `--max-attachment-mb 20` | 附件上限；跳过时明确提示分析不完整 |

控制台接入位置：

1. `server/builtin-tasks.ts`注册两个内置区级任务，更新内置目录版本，供旧安装补齐新任务。
2. `server/script-details.ts`增加专用脚本说明；`crawlers/README.md`补充实际实现后的用法。
3. 先沿用现有额外参数配置和运行记录。后续增加“社区招聘”结果页时读取`catalog.json`/统一索引，并从数据库中的报名窗口重新计算当前状态，避免快照过时。
4. 全部文档与脚本默认参数保持一致；上述参数用于新增社区专用脚本，不用于原有两个通用脚本。

## 8. 运行频率及实施顺序

建议全年每6小时运行一次，不按某个固定招聘月份才启动；已经出现尚未开始或正在报名计划时，可调整为每2小时运行一次。只有新增可报名公告、报名时间变化、取消或采集异常需要提示，重复内容不反复提示。

目前代码虽然有`SchedulerService`，但`server/index.ts`明确设置`schedulerAvailable = false`，调度启动接口也会拒绝执行。新增爬虫任务不会自动获得定时运行能力；需要后续开放并验证现有调度功能。该调度器依赖服务持续运行，不会自动唤醒休眠电脑。

实施顺序：

1. 第一阶段：两个专用采集入口、分页和时间范围、正文附件、跨次状态、招聘阶段与报名时间；可手动/批量运行。
2. 第二阶段：增加岗位附件解析和资格筛选，并显示岗位数、招聘人数、符合/不符合/待确认以及对应依据。
3. 第三阶段：接入控制台定时运行、结果页和新增/变更提示；补充经验证的报名平台发现适配器。

资格筛选采用独立可修改的个人条件配置。京户需要细化到户籍区和居住区；“党员优先”不能当作“非党员不得报考”；未提供年龄、档案所在地等必要条件时显示待确认。不同年份的资格条件分别解析，不能从旧公告直接套用。

## 9. 验收场景

- 东城2025年通知公告中的社区招考可被历史补采发现；其原文与附件均保留。
- 朝阳2026年6月2日社区招聘公告位于第二页、最新10条之后，仍能发现。
- 2027年新增公告无需修改脚本；2026年底发布的2027年招聘及跨年报名窗口正常处理。
- 重复运行新增公告数为0；同网址改正文或附件识别为更新。
- 地区与标题相同但单位/批次不同不误合并；转载保留来源并避免重复计算计划。
- 考试、成绩、拟录用、按原成绩递补均不误判为新报名。
- 报名延期、取消、多个窗口、日期没有时刻和无法解析的时间分别有明确结果。
- 单页旧置顶条目不截断扫描；触及上限或页面改版显式报告覆盖不完整。
- 请求失败、中断和服务重启后可恢复；失败附件可重试，正常无匹配与解析失败区分。
- 两个专用任务可按现有runner协议运行，通用招聘任务的行为与离线测试继续通过。

设计边界：覆盖声明以成功扫描的信息源、日期范围和解析结果为准。发现新年度公告依靠持续运行和有效来源，不等于保证某区每年都招聘。
